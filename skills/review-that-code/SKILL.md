# Review That Code!

A structured, multi-axis review process to evaluate code health, catch regressions, and ensure maintainability without blocking progress.

## Overview

Code review is the primary quality gate before changes reach `main`. Every change gets reviewed across five core axes: correctness, readability, architecture, security, and performance. The standard for approval is continuous improvement: approve code that definitely improves overall health, even if it is not how you personally would have authored it.

## When to Use

Use this skill when:
- Reviewing pull requests or uncommitted diffs before merging.
- Evaluating code generated by yourself, another agent, or a collaborator.
- Assessing refactorings or verifying bug fixes and their accompanying regression tests.

When NOT to use:
- Running mechanical linters and auto-formatters (run prettier, eslint, or ruff directly).
- Managing git branches, save points, or commit history (use `git-keeper`).
- Auditing repository documentation, docstrings, or directory alignment (use `audit-align`).

## Core Review Process

```
[1. Context & Scope] ──> [2. Tests & Behavior] ──> [3. Five-Axis Audit] ──> [4. Categorized Feedback] ──> [5. Verdict]
```

### Step 1: Understand Context & Scope

1. **Verify the Requirement**: Understand the problem being solved. What is the intended behavior change?
2. **Check Diff Sizing**:
   - Ideal: ~100–300 lines changed.
   - Large changes (>500 lines): Check if refactorings are tangled with functional changes. If so, request splitting them into separate reviews.
3. **Check Dependencies**: Ensure new packages are strictly necessary, lightweight, and actively maintained. Avoid adding dependencies for trivial tasks.

### Step 2: Review Tests First

Tests clarify intent and reveal edge-case thinking:
- Does the change include automated tests?
- For bug fixes, does a regression test reproduce the original defect?
- Do tests assert behavior and outcomes rather than internal private implementation details?
- Are edge cases (null, empty inputs, boundaries, error paths) tested?
- For testing conventions and mocking, see [testing-patterns.md](../../references/testing-patterns.md).

### Step 3: Five-Axis Evaluation

Inspect each changed file through five critical lenses:

1. **Correctness**:
   - Does the implementation match the specification?
   - Are error cases and exception handling robust?
   - Are there off-by-one errors, unhandled promises, or race conditions?
2. **Readability & Simplicity**:
   - Are variable and function names self-descriptive?
   - Is control flow simple and direct? Avoid nested conditionals and excessive abstraction.
   - Is there dead code, commented-out logic, or unused variables?
3. **Architecture & Boundaries**:
   - Does the code respect existing module boundaries?
   - Are type definitions explicit (avoiding unnecessary `any` or loose casts)?
   - Does refactoring reduce complexity rather than just shuffling code around?
4. **Security**:
   - Is all input from external sources (HTTP params, headers, files) validated at system boundaries?
   - Are queries parameterized to prevent SQL/command injection?
   - Are sensitive credentials or tokens excluded from code and logging?
   - For deep vulnerability checklists, see [security-checklist.md](../../references/security-checklist.md).
5. **Performance**:
   - Are there N+1 query patterns, unbounded loops, or missing pagination on collections?
   - Are expensive calculations cached or kept out of hot execution loops?
   - For Web Vitals and query analysis, see [performance-checklist.md](../../references/performance-checklist.md).

### Step 4: Categorize Findings with Explicit Severities

Always tag review comments with a severity prefix so the author understands priority:

| Prefix | Meaning | Required Action |
|---|---|---|
| **[Critical]** | Blocks merge | Security vulnerability, data loss, broken requirement, or build failure. |
| **[Required]** | Blocks merge | Architectural defect, missing test, or bug that must be resolved. |
| **[Consider]** | Non-blocking | Suggestion or alternative approach for future improvement. |
| **[Nit]** | Non-blocking | Trivial style preference or typo. Author may choose to skip. |

When identifying an issue, propose a concrete solution or pattern rather than vague criticism.

### Step 5: Deliver a Clear Verdict

Conclude the review with an unambiguous status:
- **Approve**: Code improves codebase health; minor nits may be addressed at author's discretion.
- **Request Changes**: Explicit `[Critical]` or `[Required]` items must be resolved before merge.

## Common Rationalizations

| Rationalization | Reality |
|---|---|
| "The code works and passes tests, so deep review isn't needed." | Tests verify what the author thought to test. Review catches security flaws, architecture drift, and maintainability traps. |
| "We'll clean up the messy architecture in a follow-up PR." | Deferred cleanup rarely happens. Address structural issues before code merges into `main`. |
| "AI-generated code looks clean and confident, so it's probably fine." | AI models frequently introduce plausible-looking hallucinations, subtle off-by-one bugs, and security oversights. Review with high scrutiny. |
| "It's just a quick dependency bump, no review needed." | Dependency bumps can introduce breaking API shifts or vulnerabilities. Inspect changelogs and lockfile diffs. |
| "This refactoring makes the code much cleaner." | Moving code between files without simplifying the logical flow or reducing concepts is not an improvement. |

## Red Flags

- Rubber-stamping (`"LGTM"`) without verifying requirements or running tests.
- Massive PRs (>500 lines) combining unrelated features, refactors, and formatting changes.
- Unlabeled comments leaving the author confused about what is blocking vs optional.
- Bug fix PRs submitted without accompanying regression tests.
- Hardcoded credentials, secrets, or local file paths in diffs.
- Adding heavy third-party packages for simple tasks that standard libraries handle.

## Verification Checklist

Before finalizing your code review:

- [ ] Requirements and task context are verified against actual implementation.
- [ ] Automated tests (including regression tests for bug fixes) pass.
- [ ] Code evaluated across all 5 axes: Correctness, Readability, Architecture, Security, and Performance.
- [ ] All feedback points include explicit severity tags (`[Critical]`, `[Required]`, `[Consider]`, `[Nit]`).
- [ ] No secrets, credentials, or dead code introduced.
- [ ] Code meets the project [definition-of-done.md](../../references/definition-of-done.md).
- [ ] Unambiguous verdict delivered (`Approve` or `Request Changes`).
