# TDD Implementation Loop

A disciplined execution workflow that builds features ticket-by-ticket using strict Test-Driven Development (Red, Green, Refactor) and creates atomic git save points.

## Overview

The temptation to write code first and backfill tests later almost always results in tests that test implementation details, miss critical edge cases, or get skipped entirely. When errors arise, agents without save points enter chaotic debugging loops, editing files blindly and breaking previously working code.

`tdd-implement` represents the **Execution Engine** in Stage 4 (Implementation) of the AI-Native SDLC. It takes the concrete `plan.md` created by [plan-that-ticket](../plan-that-ticket/SKILL.md), walks through each micro-step with strict Red-Green-Refactor discipline, executes the ticket's deterministic verification command, commits an atomic save point via [git-keeper](../git-keeper/SKILL.md), and checks off the ticket in the master plan.

## When to Use

Use this skill when:
- A ticket micro-plan (`plan.md`) has been created by [plan-that-ticket](../plan-that-ticket/SKILL.md).
- Actively writing source code and tests for a specific ticket.
- Executing iterative Red-Green-Refactor cycles on isolated tasks.
- Explicitly invoked via phrases like: `"tdd implement"`, `"run tdd"`, `"execute ticket"`, or `"implement plan"`.

When NOT to use:
- Generating the feature specification or high-level tickets (use [spec-driven-dev](../spec-driven-dev/SKILL.md) or [make-those-tickets](../make-those-tickets/SKILL.md)).
- Preparing the ticket micro-plan and inspecting target files (use [plan-that-ticket](../plan-that-ticket/SKILL.md)).
- Multi-axis code reviews or final PR approvals (use [review-that-code](../review-that-code/SKILL.md)).

## Core Workflow

```
[1. Ingest plan.md] ──> [2. RED: Failing Test] ──> [3. GREEN: Minimal Pass] ──> [4. REFACTOR] ──> [5. Verify & Save Point]
                             ▲                                                      │
                             └──────────────── Next Micro-Step ─────────────────────┘
```

---

### Step 1: Ingest Ticket Micro-Plan

1. **Load `plan.md`**: Ingest the micro-plan generated by [plan-that-ticket](../plan-that-ticket/SKILL.md).
2. **Confirm Clean State**: Run `git status` via [git-keeper](../git-keeper/SKILL.md) to ensure working directory is clean before making changes.
3. **Verify Test Runner**: Run the test runner once on existing tests to establish a passing baseline.

---

### Step 2: The Red-Green-Refactor Micro-Cycle

Execute each micro-step sequentially. Never write implementation code before a failing test exists.

#### 1. RED — Write the Failing Test First
- Write the specific test case defined in the micro-step in the target test file.
- Follow test patterns from [testing-patterns.md](../../references/testing-patterns.md) (test public behavior, avoid excessive mocking).
- **Run the test runner**: Confirm that the test **fails**.
- *Crucial check:* Verify that the test fails for the *expected business logic reason* (e.g. function returns wrong value, error not thrown), NOT because of a syntax error, bad import, or compilation crash.

#### 2. GREEN — Implement Minimal Passing Code
- Write the minimal code in the target implementation file required to make the failing test pass.
- Resist adding extra features, speculative abstractions, or handling unrequested scenarios.
- **Run the test runner**: Confirm that the test **passes**.

#### 3. REFACTOR — Clean Up While Green
- Refactor the newly added code for readability, simplicity, and strict typing.
- Remove duplicate logic, inline temporary variables, and ensure naming matches `GLOSSARY.md`.
- **Re-run the test runner**: Ensure all tests remain green.

---

### Step 3: Full Ticket Verification

Once all micro-steps in `plan.md` are complete:

1. **Run the Full Ticket Verify Command**:
   Execute the exact command specified in the ticket (e.g., `npm test tests/services/billing.test.ts`).
2. **Run Static Checks**:
   Run the project's linter and type-checker to ensure zero regressions:
   ```bash
   npm run typecheck
   npm run lint
   ```
3. **Inspect the Diff**:
   Run `git diff` to confirm:
   - Changes are strictly confined to the files listed under `File Targets`.
   - The diff size matches the expected ~100–300 lines limit.
   - No temporary debug logs (`console.log`, `print`), commented-out code, or unintended edits exist.

---

### Step 4: Atomic Save Point & Git Commit

Follow [git-keeper](../git-keeper/SKILL.md) to record the verified slice:

1. Stage only the targeted files:
   ```bash
   git add <target-files>
   ```
2. Commit with an atomic conventional commit message:
   ```bash
   git commit -m "feat(<scope>): <description of capability delivered in ticket>"
   ```
3. This commit serves as a reliable save point. If subsequent work fails, you can safely restore to this known-good state.

---

### Step 5: Update Master Plan & Loop to Next Ticket

1. **Mark Ticket Complete**:
   Open the master plan index (`docs/tasks/<feature>/README.md`) and check off the completed ticket:
   ```markdown
   - [x] [01-data-model.md](./01-data-model.md): Core billing model and validation
   ```
2. **Check for Remaining Tickets**:
   - If more tickets remain in the plan: Hand off to [plan-that-ticket](../plan-that-ticket/SKILL.md) for Ticket $N+1$.
   - If all tickets for the feature are completed: Hand off to Stage 5 ([review-that-code](../review-that-code/SKILL.md)) for the final multi-axis review.

---

### Downstream Pipeline Handoff

```
make-those-tickets  ──>  plan-that-ticket  ──>  tdd-implement  ──>  [All Tickets Done?]
                       (Creates plan.md)     (Red-Green-Save)           │
                             ▲                      │                   ├─ No  ──> plan-that-ticket (Next)
                             └──────────────────────┘                   └─ Yes ──> review-that-code (Stage 5)
```

## Common Rationalizations

| Rationalization | Reality |
|---|---|
| "I'll write the code first because I already know how it works." | Writing code first creates confirmation bias in tests, causes edge cases to be forgotten, and leads to untestable designs. |
| "Running the test before implementing is a waste of time; of course it fails." | Verifying that the test fails confirms the test is actually testing the right code and fails for the right reason. |
| "I can implement two tickets together since they touch the same file." | Combining tickets creates oversized diffs (>500 lines) that violate review standards and make regressions hard to isolate. |
| "I'll commit all tickets at the end when the whole feature is done." | Without atomic commits after each ticket, you have no save points to roll back to when an error occurs. |

---

## Red Flags

- Editing implementation code before running and observing a failing test.
- Tests failing because of a typo or import error rather than the asserted condition.
- Adding dependencies or modifying files not specified in the ticket's `File Targets`.
- Committing without running the ticket's full verification command and static checks.
- Leaving `console.log`, `TODO`, or commented-out code in the committed save point.

---

## Verification Checklist

Before marking a ticket complete and closing this skill:

- [ ] Every micro-step executed through RED (failing test) $\rightarrow$ GREEN (passing code) $\rightarrow$ REFACTOR.
- [ ] Confirmed test failed for the expected business logic reason before implementing code.
- [ ] Only minimal code required to pass tests was written.
- [ ] Full ticket verification command and static checks passed with zero errors.
- [ ] Diff inspected: strictly within target files, sized ~100–300 lines, no dead code.
- [ ] Atomic save point committed via [git-keeper](../git-keeper/SKILL.md) with conventional commit format.
- [ ] Ticket marked complete (`- [x]`) in `docs/tasks/<feature>/README.md`.
